# FURPS+: цифровизация депозитов и кредитов банка «Стандарт»

Требования со звёздочкой архитектурно значимые

## Депозитное направление, MVP

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | На сайте новый клиент видит список депозитов с актуальными ставками. | Сайт сейчас показывает только маркетинговую информацию. |
| F2  | На сайте новый клиент подаёт заявку на депозит, указав телефон и Ф. И. О. | |
| F3* | Заявка с сайта попадает в систему кол-центра. Менеджер изучает её, звонит клиенту и может предложить особые условия. | Сейчас сайт ни с чем не интегрирован, связь нужно создать. |
| F4  | После звонка новый клиент приходит в отделение для идентификации, и там открывается депозит. | Банк не может принять нового клиента без личной проверки документов. |
| F5* | В интернет-банке клиент видит депозиты с актуальными ставками и персональные ставки для себя. | Персональные ставки зависят от данных АБС, см. +R5. |
| F6  | В интернет-банке клиент подаёт заявку на депозит, указав счёт и сумму. | |
| F7* | Подачу заявки клиент подтверждает СМС-кодом. Функциональность реализуется силами команды разработки банка, без доработки ядра интернет-банка подрядчиком. | СМС реализованы в ядре, его доработка зависит от подрядчика, и этого лучше избежать. |
| F8* | Ставки ведутся в единой системе вместо XLS-файлов. С ними работают сотрудники бэк-офиса депозитов и бэк-офиса кредитов. | В исходных данных предложена АБС как возможное место, см. +R8 про разграничение доступа. |
| F9  | Согласование ставки по заявке выполняется в единой системе, возможно в АБС, а не письмами. | Сейчас процесс идёт через почту и Excel. |
| F10 | Заявку обрабатывает менеджер бэк-офиса: подтверждает условия депозита в АБС. | Автоматическая обработка относится к финальному состоянию, см. S3. |
| F11 | Клиент получает СМС после подтверждения размера ставки и после открытия депозита. | |
| F12 | Клиент видит статус своей заявки в интернет-банке. | Добавлено: без статуса клиент будет звонить в кол-центр, а он и так рискует быть перегруженным. |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейс подачи заявки максимально удобен для клиента. | Цель в формулировке бизнеса, нужно уточнить метрику, например долю завершённых заявок. |
| U2  | Интерфейсы соответствуют системе дизайна банка: привычные цвета и брендированные элементы. | |
| U3  | Интерфейс понятен людям старшего возраста: крупный читаемый текст, короткие шаги, телефон кол-центра на экране заявки. | Добавлено: это основная категория клиентов банка, и новые процессы могут быть для неё сложными. |
| R   | Надёжность (Reliability)           |              |
| R1* | Все сервисы процесса работают 24/7 с доступностью 99,9%. | Это около 8,8 часа простоя в год. |
| R2* | При сбое ЦОД сервисы интернет-банка остаются доступными и выдерживают требуемую нагрузку. | Сейчас работа идёт в одном ЦОД на одной группе серверов, при сбое можно переключиться на резервный ЦОД. Команда интернет-банка считает требование пока невыполнимым: клиентов мало, и даже день простоя сейчас не создаст проблем. Это конфликт, его нужно решать архитектурно. |
| R3* | Отказ или перегрузка АБС не мешают клиенту подать заявку: она сохраняется и обрабатывается позже. | Добавлено: доступность 99,9% нельзя получить, если онлайн-канал синхронно зависит от перегруженной АБС. |
| R4* | Заявки и события о статусе не теряются и не обрабатываются дважды. | Добавлено: повторная обработка заявки в финансовом процессе создаст лишний депозит. |
| R5  | Ставка, показанная клиенту, актуальна: есть дата действия и понятное поведение при задержке обновления. | Добавлено: ставка обновляется ежедневно, и клиент не должен увидеть устаревшую как действующую. |
| P   | Производительность (Performance)   |              |
| P1* | Отклик по операциям интерфейса составляет миллисекунды: допущение для согласования, p95 не более 300 мс для чтения и не более 500 мс для записи заявки. | Бизнес указал только «миллисекунды». Значения добавлены, потому что без чисел требование нельзя проверить. |
| P2  | Справочные данные при проведении платежей загружаются быстрее секунды. | Сейчас некоторые загружаются больше секунды. Требование вне депозитного процесса, но названо бизнесом. |
| P3* | Новые онлайн-заявки не увеличивают нагрузку на БД АБС сверх согласованного лимита. | База уже перегружена, а масштабируется только вертикально. Лимит добавлен: команда АБС должна назвать допустимую нагрузку, иначе требование нельзя проверить. |
| P4* | Новые сервисы масштабируются горизонтально, запросы равномерно распределяются между серверами, приложениями и ЦОД. | |
| P5  | Нужно определить профиль нагрузки: число клиентов, заявок в день и пик после маркетинговой кампании. | Добавлено: в исходных данных этих чисел нет, а от них зависят размеры всех компонентов. |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Разрабатывается документация для дальнейшего расширения системы: API, события, правила интеграции. | |
| S2  | Изменения в процессе депозитов не требуют обновления ядра интернет-банка. | Обновление ядра привязано к подрядчику. |
| S3* | Решение расширяется до финального состояния: автоматическое открытие депозита без бэк-офиса, а также другие продукты. | Цель бизнеса на год. |
| S4  | Заявку можно отследить по всем системам, есть единые логи, метрики и оповещения. | Добавлено: процесс проходит через несколько команд, без сквозного идентификатора разбирать сбои будет долго. |
| S5  | Есть контур интеграционного и нагрузочного тестирования, включая отработку отказа ЦОД. | Добавлено: требования R2 и P3 нельзя подтвердить без таких проверок. |
| +R  | + Ограничения (Restrictions)       |              |
| +R1* | По возможности используются технологии, которые уже есть в банке, например СУБД MS SQL и Oracle. | |
| +R2* | Новые технологии совместимы с платформами разработки банка, и внутри банка есть экспертиза хотя бы на уровне языков программирования. | В банке есть C#/.NET, Java (команда АБС), Python, PHP, Delphi, PL/SQL, React.js. |
| +R3* | Очереди сообщений строятся на Kafka. Текущая версия платформы интернет-банка с Kafka несовместима. | Нужен промежуточный сервис на совместимом стеке. |
| +R4* | Перевод интернет-банка на микросервисы возможен только в рамках задачи открытия депозитов. | Весь монолит сейчас не переписываем. |
| +R5* | В новом процессе интернет-банк не работает напрямую с API и БД АБС. | В исходных данных сказано про API. БД добавлена: сейчас интернет-банк интегрирован именно через неё, а она перегружена. |
| +R6* | АБС масштабируется только вертикально из-за своей базы данных. | |
| +R7* | Данные с сайта и из интернет-банка защищаются шифрованием трафика. | Предлагается TLS 1.2 и выше. Нужно уточнить у безопасности, нужны ли российские криптоалгоритмы. |
| +R8* | Сотрудники депозитов и сотрудники кредитов не имеют доступа к данным друг друга. | Требование безопасности из описания текущего процесса. Единый реестр ставок (F8) не должен его нарушить. |
| +R9* | Хранение и обработка персональных данных соответствует 152-ФЗ, форма на сайте содержит согласие на обработку и защиту от автоматических заявок. | Добавлено: на сайте собираются телефон и Ф. И. О., а открытая форма уязвима для спама и злоупотреблений СМС. |
| +R14* | Система кол-центра — платформа подрядчика, её сопровождает и дорабатывает подрядчик. Платформа расширяема, и специалисты команды АБС с опытом Java могут вносить изменения сами. | Из блока «IT-ландшафт». Влияет на F3: приём заявок с сайта нужно реализовать в этой системе, согласовав изменения с подрядчиком. |

## Кредитное направление

Нефункциональные требования те же, что для депозитов: U1–U3, R1–R5, P1, P3–P5, S1–S5, +R1–+R9. Ниже только то, что добавляется.

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F13* | На сайте новый клиент видит предложение кредита со ставкой. Полные условия хранятся в Кредитном конвейере. | Конвейер становится источником условий для онлайн-каналов. |
| F14 | На сайте клиент подаёт заявку на кредит, указав телефон и Ф. И. О. | |
| F15* | Если клиент добавил паспортные данные, он сразу получает решение об одобрении или отказе на основе данных скоринга. | Клиент новый, поэтому доступны только общие данные бюро кредитных историй. |
| F16 | После подачи заявки на сайте клиент получает СМС, что нужно прийти в отделение для идентификации и получения кредита. | |
| F17* | В отделении менеджер продолжает работу с той же заявкой, если клиент получил предварительное одобрение на сайте. Для нового клиента он создаёт новую заявку через АБС. | Заявка должна быть одной в АБС, конвейере и онлайн-каналах. |
| F18 | В интернет-банке клиент видит доступные кредиты с актуальными условиями, как на сайте. | |
| F19* | В интернет-банке клиент видит предодобренное предложение, если по нему уже был скоринг и рассчитана приемлемая сумма. | |
| F20 | В интернет-банке клиент подаёт заявку, указав счёт зачисления и данные заявки, и подтверждает её СМС-кодом. | Используется сервис кодов из F7. |
| F21* | После подачи заявки по предодобренному предложению скоринг повторяется по упрощённой процедуре, если ситуация изменилась. | |
| F22 | Клиент получает СМС при изменении статуса заявки на кредит. | |
| F23 | Клиент видит статус заявки на кредит в интернет-банке. | Добавлено: то же обоснование, что у F12. |
| P   | Производительность (Performance)   |              |
| P6* | Заявка по предодобренному предложению обрабатывается в течение того же рабочего дня. | Сейчас заявки попадают в конвейер из АБС раз в сутки. |
| P7* | Клиент получает решение по заявке в течение одного дня, если данных достаточно. | Цель бизнеса на год. Для обычного процесса сейчас это неделя. |
| P8* | Решение на сайте по паспортным данным приходит за время одной сессии: допущение для согласования, не дольше 30 секунд. | Добавлено: обещание «сразу» нужно проверять, а время зависит от внешнего бюро. |
| P9* | Система скоринга не получает дополнительной нагрузки от предрасчётов. | Система важна для банка и нагружена в рабочие часы. |
| R   | Надёжность (Reliability)           |              |
| R6* | Недоступность бюро кредитных историй не теряет заявку: клиенту сообщают, что решение придёт позже. | Добавлено: бюро внешнее, и решение на сайте от него зависит. |
| +R  | + Ограничения (Restrictions)       |              |
| +R10* | Ускорить обмен между БД АБС и конвейера или проводить его чаще невозможно. | Нужен отдельный путь онлайн-заявок. |
| +R11 | Кредитный конвейер и система скоринга масштабируются горизонтально и работают 24/7. | Это даёт возможность нагружать их онлайн-заявками, но не предрасчётами (P9). |
| +R12* | Перед запросом в бюро кредитных историй клиент даёт согласие, а телефон подтверждён кодом. | Добавлено: запрос кредитной истории требует согласия субъекта (218-ФЗ), а каждый запрос может стоить денег и его нужно защищать от злоупотреблений. |
| +R13* | Паспортные данные передаются и хранятся только в защищённом контуре: сайт их не сохраняет. | Добавлено: сайт находится в публичной зоне, а паспорт относится к чувствительным данным. |
| +R15* | Кредитный конвейер — коробочное решение на Camunda и Oracle. Часть доработок выполняет подрядчик, а обработчики на Java и описания процессов могут менять специалисты IT-отдела. | Из блока «IT-ландшафт». Влияет на F13, F17 и P6: новый путь онлайн-заявок и публикацию условий нужно встроить в конвейер. |
